The philosophy

Strategy belongs in the harness.
Not in the model.

Every failure we traced came back to language, sequencing, or checking, not raw intelligence. So the harness owns those jobs. The model gets one small, clear piece of work at a time, a contract it helped write, and a checker that says exactly what went wrong. Executive function belongs in code, where it can be tested, not in a prompt, where it can only be hoped for.

And it runs locally, on hardware people already own, with no API bill. Capability should not have to be rented by the token.

The philosophy, in six principles

Do not make the model smarter.
Make the work checkable.

Each mechanism in the harness exists because a failure taught us where a job really belongs: in the model, or in the code around it. Almost every time, the answer was the code.

2. Verify in code, not on trust

4. Treat failure as feedback

Measure twice, cut once.

When a check fails, the checker stops being a grader and becomes a teacher. Its exact failure message goes back as the next instruction.

Where this goes next

The same philosophy,
expanded to do more.

The harness grows the way it was built: one honest failure at a time. Each expansion below moves another job out of the model and into code, or turns one hard-won lesson into something reusable.

More of the plan checks itself

Richer verification.

Today about half of all Then clauses verify deterministically; the rest are taken on trust. Give verifiers the full picture of a step, its tool calls, its captured output, its sub-run result, and add command and output verifiers. Every point of hit rate gained is a step no one has to take on faith.

A library that keeps growing

Knowledge gaps, filled permanently.

The suggestion library starts with one idiom a 2B model was missing. It grows into packs: files and data, documents, spreadsheets, research with sources. A gap only has to be discovered once. After that, every future plan gets the idiom for free.

Tools that absorb whole loops

Never hand the model a loop it can hallucinate.

grep_files exists because listing and scanning files by hand gave the model filenames it could invent. That pattern generalises: whenever a job is a loop the model would have to narrate, the loop becomes a tool, and the model goes back to choosing and judging.

Plans people can reuse

Approved work becomes a template.

A Gherkin plan a human has reviewed and approved should not be thrown away. Saved plans become a library of trusted recipes: recurring research, data clean-up, document drafting, household and project chores, each one re-runnable and re-checkable.

Bigger tasks, chained plans

Decomposition, all the way up.

If a step is too big, it gets its own plan. Plans can call plans, with checkpoints a human can inspect between them. That is how you get from five micro-tasks to an afternoon of real work without ever asking the model to hold the whole job in its head.

Any model, same harness

Scale the model only if you want to.

Nothing in the harness is specific to one model. Run it with a 2B model on a laptop, a larger model on a workstation, or split the roles, one model planning and a smaller one executing. The philosophy does not change with the parameter count, and neither does the contract.

Questions, answered

The useful things to know before you run it.

What it is, what it needs, and what happens when a check fails.

What does agent-harness actually do?+

It gives a small local language model a set of jailed tools, a reviewed plan, and a verification loop. The model proposes and executes small steps. The harness owns the strategy, the checks, and the retries.

Why not just use a bigger model?+

Bigger models fail differently, not less: in our eval the 4B model was slower and sloppier, with literal placeholders in its plans. Every capability moved into the harness is capability that does not require a bigger model, so the work runs on smaller machines.

Does the harness run unattended?+

Only if you ask it to. The default workflow is review-first: the agent proposes a Gherkin plan, you edit and approve it, and only then does anything execute. Auto mode exists, but review is the point.

What do I need to run it?+

Python 3 and Ollama with a small model pulled, for example gemma4:e2b. The harness itself is zero-dependency standard library Python. Set HARNESS_ENDPOINT if Ollama lives on another machine.

What happens when a check fails?+

The checker's exact failure message becomes the next instruction, and the run retries on the same workspace: fix only, never redo. Per-step verification gets one retry, then warns and continues, because the task checker is the final judge of correctness.

What is Gherkin doing here?+

Gherkin is the bridge language: a plain-language contract that the human and the agent can genuinely agree on. The plan states observable outcomes. The agent stays free on the how.

How far can this expand?+

Along the lines it already grew: more verifiers so fewer steps are taken on trust, a bigger suggestion library so gaps are filled once and for all, tools that absorb whole loops, reusable approved plans, and chained plans for bigger jobs. The model can stay exactly the same size while the harness around it gets better at its job.

Is it really zero dependencies?+

Yes. Pure Python 3 standard library, talking to your local Ollama server. No packages to install, no API keys, no cloud.
